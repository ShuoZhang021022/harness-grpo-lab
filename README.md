# Learning an LLM Agent's Harness with GRPO

[English](README.md) | [简体中文](README.zh-CN.md)

This project studies whether GRPO with LoRA can improve a main agent's selection and generation of Python tools. A fixed external solver uses the supplied tools to write and execute a Python solution. A fixed external similarity judge checks newly generated tools. Only the main agent is trained.

The repository implements the tool library, trajectory control, GRPO core, datasets, reporting, and plotting. All project prompts are in English and request English natural-language output while preserving required answer formats and program interfaces. The model configuration selects self-hosted Qwen3-8B for the trainable main agent and frozen solver, and Qwen3-32B for the frozen similarity judge and offline reference auditor. Real model adapters and an isolated execution backend are still missing. No model weights have been downloaded or loaded, and no real LLM training or evaluation has run. Numerical test fixtures and test-rendered charts are not experimental results.

## Confirmed research design

The main agent sees only the problem description and the initial tools' textual descriptions and interfaces. It configures tools through autoregressive generation before execution, without execution feedback or subsequent rescheduling. Implementation agents are Python tools that cannot call LLMs. The initial library contains 50 tools. Newly generated tools are available only within their trajectory; execution copies are deleted afterward. Generated tokens, source code, and judging reasons remain in training and audit records. LoRA updates cover every token generated by the main agent, including tool selections, descriptions, and new tool code. The external solver, similarity judge, and execution environment do not participate in gradient computation. Each batch contains 100 questions with eight independent trajectories per question. One full gradient update follows all 800 trajectories; the next batch uses the updated weights. Each trained system uses 30 batches, 30 updates, and 24,000 trajectories in one pass over the training set. The objective is the original sequence-averaged clipped GRPO loss. Rewards are centered and divided by their standard deviation within each question's group of eight. The clipping parameter is 0.2 and the KL coefficient is 0. Ordinary reward subtracts 0.01 per supplied tool from correctness (+1 for success, -1 for failure). Similarity rejection terminates the trajectory immediately with a final reward of exactly -1, overriding tool costs. Consequently, rejection can receive a higher reward than an ordinary failed trajectory with tool costs. Each new tool is checked against all 50 initial tools and previously accepted tools in the current trajectory. It is rejected if a single reference tool can substantially replace its core functionality. This check concerns functional duplication; it does not establish reuse across tasks or exclude task-specific solutions. The solver prompt requires substantive use of every supplied tool. Each of the three domains has 1,000 training questions and 100 test questions. Every system receives the same test set, with eight independent attempts per question: 9,600 test trajectories across four systems. The four systems are the solver with all 50 fixed tools; an untrained main agent that selects and generates tools; an independently trained selection-only main agent; and an independently trained main agent that selects and generates tools. The two trained systems start from the same initial weights and each receive a 24,000-trajectory training budget. Training questions are shuffled once. There are no additional rewards, regularizers, or automatic failure retries.

## Current implementation choices

These details describe the existing implementation, including choices disclosed during the implementation audit. Listing them here does not imply that every detail was separately confirmed. The English conversion changes wording, not these behaviors. The 50 initial tools comprise 18 math tools, 17 code tools, and 15 life-scenario tools. Catalog entries include interface examples. Tools also prohibit network access and execution of supplied Python source code. The main agent emits select, create, and finish actions in JSONL. A new tool can be one Python file or a multi-file package with an explicitly declared entry point accepting an arguments object. A package counts as one tool. Accepted new tools are automatically selected; repeated selections of the same tool are counted once. Selecting no tools is currently allowed. Generated code is validated before similarity judging. Invalid actions or code can therefore terminate a trajectory before the judge runs. Infrastructure failures are saved without a reward and stop the batch without a retry. Failed or zero-variance groups are not automatically skipped, and training does not stop early. Tool-call coverage is diagnostic only, with no additional penalty for violating the solver prompt. A recorded call alone does not prove that its result was used substantively. The solver's permitted business logic and authority to modify tools remain unspecified. Numeric settings are LoRA rank 32, alpha 64, dropout 0; learning rate 1e-5; AdamW with weight decay 0; population standard deviation (correction=0) and epsilon 1e-8. There is no gradient clipping, entropy bonus, or additional loss. Qwen3-8B is selected; LoRA target layers, exact model revisions, and thinking modes remain unset. Training shuffle seed is 20260920; the evaluation seed list currently contains only 20260920. The reference updater uses one trajectory per microbatch and accumulates all 800 trajectories before one optimizer step. It disables dropout while retaining gradients and permits gradients only for LoRA parameters. Answer parsing, task-generation rules, dataset filters, and error handling are existing implementation decisions. Their research implications still require review; translation does not resolve them.

## Self-hosted models

All LLM roles use downloadable Qwen weights on user-provided compute. The model_access setting is self_hosted_open_weights; no paid model-provider API is part of the selected setup.

| Role | Model | Parameter updates |
|---|---|---|
| Main agent | Qwen/Qwen3-8B | LoRA only |
| Solver | Qwen/Qwen3-8B | Frozen |
| Similarity judge | Qwen/Qwen3-32B | Frozen |
| Offline reference-answer auditor | Qwen/Qwen3-32B | Frozen |

The official [Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B) and [Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B) repositories list the Apache 2.0 license. Self-hosting avoids per-request model-provider API charges; GPU hardware, hosting, and electricity still have costs.

Two base model checkpoints are selected. The main agent and solver both start from Qwen3-8B, but the solver must retain its original frozen parameters and must never receive the main agent's trained LoRA adapters. The similarity judge and offline auditor can share one self-hosted Qwen3-32B service, with separate requests, prompts, and contexts. The offline auditor must not pass reference answers to online agents. Using the same model for several roles does not provide independent evidence that its judgments or answers are correct; hidden tests, exact-answer checks, and reference verification retain their existing roles.

The selected model IDs and offline-auditor settings are recorded in configs/experiment.json. Revisions, thinking modes, sampling settings, service endpoints, and GPU allocation remain unresolved. No new quantization, decoding mode, or resource allocation is assumed. Qwen3 requires Transformers 4.51.0 or later, reflected in the training dependency minimum; final dependency versions remain to be pinned. Deployment can use a [self-hosted vLLM endpoint](https://qwen.readthedocs.io/en/latest/deployment/vllm.html), but real model and execution adapters are not yet implemented.

## Datasets

`data/public/train.jsonl` and `data/public/test.jsonl` contain 3,000 and 300 tasks. Separate math, code, and life train/test JSONL files are also provided. All task descriptions are in English.

`data/public/assets/<task_id>/buggy.py` contains the program for each of the 1,100 code-repair tasks.

`data/private/labels/verifiers.jsonl` contains answers, hidden tests, and reference implementations. It must not be mounted in the agent environment.

`artifacts/dataset_audit/audit.json` records source revisions and hashes, filters, splits, counts, and verification status.

The math training set contains 883 AIME questions and 117 MATH Level 4/5 supplements; the math test set contains 100 AIME questions. Source mirrors are [Pandores AIME](https://huggingface.co/datasets/Pandores/aime-1983-2025) and [EleutherAI MATH](https://huggingface.co/datasets/EleutherAI/hendrycks_math). Source-provided answers have not been independently verified and must not be presented as uniformly verified official answers. The build excludes 51 AIME questions requiring embedded figures and one with an ambiguous or invalid reference. Supplements use integer-answer questions from the original MATH training split, with exact and near-duplicate text filtering.

Code tasks repair one mutated operation in a four-step integer program. Each task provides a full behavioral specification, public examples, and hidden input tests. Ordered operation sequences are disjoint across splits. Reference programs were executed and checked against a declarative oracle, and every buggy program fails at least one hidden test. This dataset supports conclusions about synthetic compositional program repair, not repository-level bug fixing.

A previously identified limitation remains: 11 of the 100 code test tasks match a training program's outputs for every integer from -500 through 500. This is evidence of functional overlap over the checked range, not a proof of equivalence for all integers. No tasks or splits were changed during translation.

Life-scenario tasks use fixed maps with 16 places and routes of eight moves. Training and test maps differ but share the generation rules. Deterministic route replay verifies each unique final place ID. The domain represents navigation in a fully specified fictional map, rather than general real-world life problems.

## Usage in PowerShell

The repository contains source code, configuration templates, prompts, public tasks, tool catalogs, and audit records. Private answers and source downloads under `data/private/`, model weights, credentials, runtime outputs, and temporary files are excluded from Git. The complete test suite below requires the local private verifier file in addition to the public tasks. A fresh clone does not contain that file; restore it locally before running the dataset test. The five code-level test modules can be run without private data:

~~~powershell
$env:PYTHONPATH='src'
python -m unittest discover -s tests -p test_tools.py -v
python -m unittest discover -s tests -p test_experiment.py -v
python -m unittest discover -s tests -p test_grpo.py -v
python -m unittest discover -s tests -p test_lora_update.py -v
python -m unittest discover -s tests -p test_plotting.py -v
~~~

Run from the project root with Python 3.11 or later. Plotting requires matplotlib and numpy, numerical GRPO tests require torch, and dataset construction requires pyarrow. Production environment and dependency versions still need to be fixed for model deployment.

~~~powershell
$env:PYTHONPATH='src'
python -m unittest discover -s tests -v
python scripts/check_experiment.py --validate-data
~~~

The readiness check returns exit code 2 when required settings are missing. It does not launch training.

~~~powershell
# Inputs must be trajectory JSONL files from actual runs. Output directories must not exist yet.
python scripts/summarize_trajectories.py --input outputs/run/batch_001/trajectories.jsonl --output outputs/report --samples-per-question 8
python scripts/plot_results.py --input outputs/test_fixed/trajectories.jsonl outputs/test_untrained/trajectories.jsonl outputs/test_selection/trajectories.jsonl outputs/test_full/trajectories.jsonl --output outputs/figures --samples-per-question 8 --comparison
~~~

Reports include `question_success.csv/jsonl`, with one row per question recording eight success flags, eight rewards, the success count from 0 to 8, statuses, batch, and policy version. `batch_summary.csv/jsonl` records batch success rates, success-count histograms, and counts of groups with zero reward variance. Success rates use the explicit `success` field, not the sign of reward. A group of failed attempts can still have nonzero reward variance when tool counts differ.

Reporting rejects duplicate, missing, or unscored samples by default. The `--allow-incomplete` option is for failure diagnosis; incomplete groups have no reported success rate. Plots include trajectory success heatmaps with question mappings, training-batch success curves, and overall and per-domain test success bars for the four systems. Training batches contain different questions, so their curves are diagnostic. Evaluation does not select the best of eight using hidden answers or claim confidence intervals or statistical significance.

## Implementation status and remaining work

The episode and training modules provide execution cores with injectable adapters. Tests cover per-tool rejection, cleanup, the 800-trajectory sampling barrier, and policy version changes. The GRPO module implements token-level loss explicitly. The LoRA updater is a single-process reference implementation, not an A100-validated distributed trainer. Whether 30 updates improve performance remains an experimental question.

Model IDs are selected in configs/experiment.json, but weights have not been downloaded or loaded. Required settings remain explicit null values: exact model revisions and thinking modes; LoRA target layers; A100 card count, memory per card, and execution host; self-hosted endpoint configuration and authentication setup; sampling settings and output limits; solver permissions; isolation backend, timeouts, and execution budgets; and independent math-reference verification. The reference-auditor settings describe the planned offline review and do not constitute a completed audit. The reported hardware wording does not establish that eight A100 cards are available. Credentials must not be committed to the repository. Formal experiments must wait for the required settings and adapters.

Method references: [DeepSeekMath GRPO](https://arxiv.org/html/2402.03300v3) and [TRL GRPO documentation](https://huggingface.co/docs/trl/main/en/grpo_trainer). This project explicitly implements the confirmed original sequence-averaged loss rather than inheriting potentially different library defaults.

See [artifacts/VERIFICATION.md](artifacts/VERIFICATION.md) for verification coverage and [artifacts/english_conversion.json](artifacts/english_conversion.json) for the historical English-conversion audit. The Chinese README and subsequent documentation edits were added after that audit. Original third-party source snapshots and scratch reference material are preserved locally in their original form and are not uploaded.
